# Inventory menu assistant

The **AI menu assistant** on Make your menu calls authenticated `POST /api/digital-menus/ai/suggest`. It uses the existing Google Gemini integration; configure `GEMINI_API_KEY` or comma-separated `GEMINI_API_KEYS` on the backend. Credentials never go to the browser.

For local development, set `VITE_API_URL=http://localhost:5050/api` in `.env.development.local` and run the backend on port 5050. A hosted API must be deployed with these changes before it can serve the new endpoint.

Production frontend builds default to `https://itemhive-8552.onrender.com/api`. A valid remote `VITE_API_URL` can override it, but localhost/loopback overrides are ignored in production. Include all new backend and frontend source files in the Git commit used for deployment; tracked controllers importing untracked files will fail the hosted TypeScript build.

Menu generation and menu import default to `gemini-3.5-flash-lite`, with `gemini-flash-lite-latest` and `gemini-3.8-flash` as fallbacks, independently of theme model settings. To configure them, set `GEMINI_MENU_MODEL` and optionally comma-separated `GEMINI_MENU_FALLBACK_MODELS` (an empty fallback value disables additional models). Models must support Gemini generateContent structured JSON output. Flash-Lite requests use minimal thinking; other Gemini 3 models use low thinking, and Gemini 2.5 Flash uses a zero thinking budget. See [Google's thinking configuration](https://ai.google.dev/gemini-api/docs/generate-content/thinking).

Users choose up to 200 inventory items, enter an optional brief, and opt into **Suggest deals / combos**. Tenant-owned item names, categories, selling/menu prices and menu preferences are sent. Custom menus can also send the merchant's selected logo, restaurant theme, brand colors and current design for style suggestions. Request-local short IDs replace database IDs to keep larger menus fast; validated results map back to inventory IDs on the server. Purchase prices, suppliers, product images, customer data, and exact stock levels are excluded. No products or prices are changed in inventory.

AI output is validated against the selected inventory. Sections cannot duplicate items. Combos contain 2–5 distinct products from suggested sections, each once, with an editable combined price. Unchecked deals are always excluded. Invalid output and provider failures leave the draft unchanged. The total provider deadline remains 45 seconds. Each attempt, including its response body, has a 15-second budget; slow, overloaded or unavailable models fall back within the remaining total time. Authentication failures stop immediately and quota failures use the next configured key. Closing the dialog discards its response.

Suggestions are reviewed before being added to the draft. Matching sections retain their styling; additional sections/pages are created as needed, with at most 15 items per generated section, 20 pages, and 100 elements. Users can continue editing afterward.

## Modern suggestions for templates and custom menus

Choose your menu only selects a template or custom canvas. Custom colors, fonts, layout and decoration are edited on **Make your menu**. The custom AI assistant always requests a complete design, colors, fonts, name and headings; each suggestion remains editable and individually optional at review. Templates offer fancy modern designs, fonts, columns and decorations using the chosen palette; the response and apply steps both discard any AI color overrides. Template names and extra headings are kept. The restaurant's saved invoice logo (or appearance logo) and saved theme colors are offered as a starting point. An untouched application default accent is not restaurant branding. Without any saved theme or logo, AI chooses a complete modern palette based on the inventory and brief, rather than inheriting blank canvas colors. Theme-only and logo-only branding both work. Users can supply or remove a logo (PNG/JPEG/WebP up to 1 MB), describe an optional restaurant theme, and give explicit preferences in the brief. The logo is sent as an inline image, never as text in the prompt, and is used for suggestions only. Explicit user instructions take priority over brand colors and AI preferences. Style requests use `includeStyle`, `currentDesign` and `brand`; older requests remain supported without these fields.

Before sending style fields, the browser checks authenticated `GET /api/digital-menus/ai/capabilities` for `custom-menu-copy` on custom menus or `template-menu-style` on templates. An older server returns 404, which displays an explicit backend-update message; templates also offer **Generate sections & deals only**. Basic requests omit every new style field, including `includeStyle: false`, so older Joi schemas continue accepting them. Do not silently discard a user's requested styling when the connected backend lacks support. Both the backend and the browser reject incomplete custom style responses instead of displaying current canvas colors as AI suggestions.

AI returns editable background, text, accent, customer header and customer card colors, a heading font, section columns, and a design: Modern Cards (rounded panels and price badges), Minimal (open spacing), or Editorial (accent dividers). Modern designs are the default; explicit requests for traditional lists, serif fonts or one column take priority. Decorations include a soft accent glow, border, corner accents or subtle dots. The provider must explain how requested artwork maps to these supported decorations. Generated text and heading colors are checked for 4.5:1 contrast on the menu and customer card backgrounds. Low-contrast AI colors are adjusted to the nearest readable shade, preserving the logo hue where possible; incompatible customer card backgrounds are matched to the menu background. The reason discloses adjustments. This normalization never runs on reviewed user edits. Custom menus also receive a suggested menu name, section names, and up to three extra headings/taglines. Existing menu names are kept unless the user explicitly checks the replacement. Every suggested name and heading can be edited or unchecked. Accepted extra headings are inserted after the title, avoid duplicates, remain editable, and respect the 100-element limit.

Each field can be edited or unchecked before applying; a style can be accepted without accepting sections or deals. Suggestions never publish automatically or replace the selected template or page order. Section widths change only if the merchant accepts Section columns; unchecking that field preserves existing widths.

Accepted colors update blocks that follow the existing theme; individually colored headings and labels keep their edits. **Menu style, colors & layout** in the builder and the custom design picker let users change the style afterward. Designs, columns and decorations persist in the draft and published snapshot and render on the menu sheet and A4 print preview. User color edits are not automatically replaced by AI colors.

Accepted combos are saved as standard child deals when saving the draft or publishing, before the publication snapshot is made. A tenant/parent/request-ID unique index makes combo save retries idempotent. Pending combos remain editable and removable before saving. Deals are included in the A4 print preview. Publishing retains the existing single-active-menu behavior.

Run `npm run test:digital-menus` in backend and `npm run test:menu-ai` in the project root for focused verification.

## Revamp an existing menu

**Upload existing menu** is available beside templates/custom and in the menu builder. Users can supply a JPG, PNG, WebP photo or PDF up to 2 MB, or paste up to 20,000 characters. Authenticated `POST /api/digital-menus/ai/import` uses the same server-side Gemini configuration and deadline. Images are decoded, oriented, resized and stripped of metadata; PDFs are passed inline to Gemini. Uploaded files and extraction results are not stored by ItemHive. The dialog identifies Google AI as the reader.

The extraction copies the menu as printed: section headings in reading order, item names, descriptions, printed prices, page numbers, whether sections sit side by side (full, half or third width), the menu name, tagline and a short customer footer (tax, hours or contact details; never payment account details). Unclear prices are returned as null and flagged for review; names and prices are never invented. Extracted output is validated and limited to 200 items, 40 sections and 20 pages. Invalid files, provider errors and malformed responses leave the current menu unchanged. Import requests may use up to 40 seconds per model attempt within the shared 45-second deadline, because a whole menu is a long structured answer.

The provider also reads the original look: background, text, heading and panel colors, serif or sans headings, title alignment, a matching visual style and decoration. Text that would be unreadable on its own background is corrected and noted; an unreadable style is dropped without losing the items. For JPG, PNG and WebP uploads, the provider returns each item photo's bounding box and the box of that item's name, and the server crops the photo from the normalized image into a small WebP (up to 320 px, at most 80 photos). A photo is kept only when it sits right beside, above or below its item's name, so large decorative plates or collages beside a list never become item photos. Tiny boxes and page-sized backgrounds are skipped. Photo uploads also return `picture`, the whole uploaded page as a WebP (up to 1600 × 2400 px and 1.1 million characters). PDFs and pasted text never produce photos. Older servers return only names, prices and pages, and the dialog then falls back to template styling.

Review includes editable section headings, pages, item names, descriptions and menu prices, with each photo shown beside its item. Only unique exact inventory-name matches are linked automatically; users can link any row to an inventory item. Super admins and admins with **Import Products** access can leave unmatched rows as new items: applying first builds and validates the whole menu, then creates them through the existing `POST /api/products/bulk` with the item name, section as category, menu price as selling price, description and cropped photo, and 0 stock, cost and minimum stock for the merchant to complete in Inventory. Other users must match or untick unmatched items. Existing inventory items are never modified and keep their own photo and description. One inventory product can be selected only once. An unclear printed price may default to the current menu/inventory selling price, with a visible confirmation reminder.

Review asks **How should your menu open?** **Keep my original picture** (the default for photo uploads) adds the uploaded page as a picture element, on page 1 when replacing or on a new page when adding pages. **Also list these items after the picture** (on by default) adds the reviewed items as orderable sections on the following pages in the picture's colors, under the menu title, so customers can order them and prices stay editable. Unticking it adds only the picture and an editable title: no inventory items are created and the menu cannot be published until items are added. Picture elements (`type: 'image'`, a PNG/JPEG/WebP data URL of at most 1.1 million characters, at most two per menu, with the description in `text`) can be moved, resized, moved to another page or deleted like any other element, and render in the builder, customer menu and A4 print. **Recreate it as an editable menu**, when replacing, recreates the original as a custom design instead: its colors, font, decoration and visual style, title and tagline, sections on their original pages with their original widths and full item lists, and the footer note on the last page. **Use my current design** uses the chosen template's typography/columns. Replacing changes the draft's name, items and menu prices. **Add as new pages** preserves the existing menu and its design and adds imported sections after it; imported products move to their new sections if already present. Template-styled imports continue sections after 15 items. All imports are subject to the existing 20-page/100-element limits. When the old menu had photos or descriptions, `design.showImages` / `design.showDescriptions` are switched on; both can be toggled in the builder for any menu. Photos and descriptions render in the builder, customer menu and A4 print. The public menu returns inventory descriptions only when the published design shows them. The result remains editable and uses the existing Save Draft, Publish and A4 print flows. Importing never publishes or replaces the live menu automatically.

## Section photos

Every section can carry `sectionImage: { url, alt }` independently from item photos. Users can upload a PNG/JPEG/WebP (up to 10 MB, resized and encoded as WebP under 200,000 characters), use a suitably sized inventory photo, select a library example, replace it or remove it. Photos move with sections, continue onto a new page with their section, and render in editing, public table menus and A4 printing. On an original uploaded menu, adding a section photo expands that text column while preserving the original surrounding artwork. Saved sections and the published snapshot retain photo metadata. Inline raster uploads and direct HTTPS image links are accepted (credential-bearing URLs are rejected). Old library paths are retained for draft compatibility; total menu image payloads are bounded to 2.4 million characters.

The assistant enables **Suggest section images** by default, checks the `section-images` capability and sends `includeSectionImages: true`. Gemini selects `imageKey` for each section from the supplied browser-sourced web-photo library (main courses, appetizers, drinks, desserts), or `none` when nothing fits or the merchant asks for no photo. It does not fabricate URLs or generate images. The frontend maps validated keys to verified Pexels image links and offers source/photographer links. Users can paste any direct HTTPS image address; it must load in the browser before the Use image link action is enabled. Remote photos use no-referrer requests and the backend does not download user-supplied URLs. Old generated-library paths resolve to the corresponding web photos. Photo suggestions can be unchecked or replaced before applying. Existing restaurant section photos are kept by default; the user must accept an AI replacement. Missing or invented provider image keys are rejected. Template colors remain locked. Modern editorial menus now use rounded photo panels and price badges instead of thin ruled lists.

## Old menu inspiration

When the draft has a picture element, or a photo was uploaded in this session, the AI menu assistant offers **Take inspiration from my old menu** (on by default). The picture is sent to `POST /api/digital-menus/ai/suggest` as `inspiration` (a PNG/JPEG/WebP data URL of at most 1.1 million characters) and reaches Gemini as a separate image labelled "Previous menu", never as prompt text. The model reuses the old menu's section names, grouping and item order wherever the selected inventory fits, adds sections for items that fit none of them, follows its look for style suggestions (template menus keep their colors), notes whether its items had photos, and lists old-menu items missing from the selected inventory in the summary. Prices always come from inventory or menu prices. The browser checks for the `menu-inspiration` capability first. Against an older server it explains that the backend needs updating and offers **Generate without my old menu**.
